ClusBot 是面向用户持续承担工作的 Personal Agent。它以用户目标为起点，通过 Router 与 Worker 两层 Agent 组织工作，由持久运行时、统一资源模型、上下文与知识机制、受控执行能力共同完成任务。集群交付与运维是其首个完整领域：用户可以委托节点交付、集群健康维护和故障处置，也可以随时交流、调整要求、查询进展与查看成果。

本设计确定 ClusBot 的系统边界、逻辑组成、核心数据、运行机制和运维领域规则之间的关系，作为后续架构图、技术方案图与时序图的共同依据。Go、React、SQLite 和本机工作区已在 Personal Agent 落地；具体集群适配器、生产参数和部署扩展仍须结合实际环境确定。

1 设计目标与系统边界

产品目标

用户向 ClusBot 交代的是希望达成或持续维持的结果。系统需要将要求转化为有责任归属、执行依据和完成标准的工作，并在用户离开对话后继续推进。遇到等待时保存状态，遇到变化时重新判断，遇到需要用户决定的问题时给出具体选项，完成后提供可追溯的结果。

集群场景覆盖资产发现、OS 部署、带内带外配置、单节点基准测试、联机测试、验收和交付；交付后继续承担监控、故障处理、自愈、工单协作、资源分派与业务调度状态维护。报告、外部应用连接、经验整理和工作主页服务于同一组目标与工作记录。

由此形成五项核心要求：

  • 多项工作能够独立推进，用户仍可与同一个 Personal Agent 持续交流。
  • 长流程能够跨等待、重启和执行者更换继续，已发生的外部动作可核对。
  • 当前资源事实、任务状态和历史经验各有权威来源，重要结论能够追溯到证据。
  • 对话、监控事件、周期触发和页面操作遵守相同的工作归属与执行规则。
  • 反馈可以改变在途工作；经验可以改善后续判断；可复用方法的变更经过用户确认。

系统内外的责任

ClusBot 内部负责用户关系、目标与任务、Agent 协作、执行计划、操作记录、上下文装配、知识维护、能力治理，以及运维领域的状态解释与控制规则。Personal Agent 包括这些组成部分；Router 和 Worker 是其中承担认知判断的两层 Agent。

设备、BMC、OS 部署系统、监控系统、测试工具、业务调度器、外部工单和消息渠道是外部执行或事实来源。ClusBot 通过适配能力查询和操作它们，保存意图、引用与确认结果。外部系统已经发生的事实不能由模型叙述替代，跨系统操作也不能假定原子完成。

通用核心统一工作与信息语义。运维领域定义资源类型、配置与健康规则、流程模板、测试和验收要求、资源占用规则及具体执行能力。领域定义参与通用核心的运行，不另行建立运维专属的目标、任务或记忆体系。

Router 与 Worker

Router 是主会话中受理自然语言的 Agent，维护用户目标、工作优先级、跨任务进展和待决事项。它结合当前会话、明确的对象和 Task 引用理解用户意图，判断工作归属，再提交对应决定。一个输入可以拆为多个意图，分别关联责任。对象、权限范围或重要取舍仍有歧义时，Router 向用户提出具体问题。

Router 识别的意图 处理结果
普通问答或查已有进度、结果 依据可读的事实和工作记录直接回答。需要新增调查时，转入已有工作跟进或新委托。
给已有任务补充信息或委托范围内的进一步处理 提交跟进及目标 Task。运行时登记在原任务内，需要新判断时唤醒当前负责的 Worker。
暂停、恢复、取消或改变现有目标、验收要求与承诺 提交作用范围明确的控制请求或修订提议。运行时核验权限和当前版本，保存控制意图或新版本，再按需要安排后续工作。
提出新委托或持续责任 明确目标、范围、约束与验收条件，提交 Task 或 Goal 提议。运行时校验并持久登记，按适用流程直接启动或分派 Worker。

Worker 对一个有边界的 Task 负责，使用任务上下文、领域知识、Skill 和工具形成计划，在授权范围内直接决定委派给它的事项，提交计划修订或执行请求，并核验结果。复杂 Task 的负责人可以提出子任务，再整合子任务成果。规划、诊断、执行、验证与知识整理都是第二层 Worker 的角色，任务树的深度不会增加固定的 Agent 层级。

Worker 的角色配置可以长期存在，活跃推理按需要启动。任务等待时保留责任与工作记录，释放当前 Run 的执行槽。执行槽是运行容量，Worker 是认知角色，外部工具进程与设备作业各有自己的生命周期。

Router 不逐项介入工具调用。范围内需要判断的进展和异常交给任务负责人；跨任务冲突、目标变化及用户必须决定的问题进入整体协调。状态变化、定时器和外部结果能够由既定规则处理时，运行时直接推进。计划可以把选组、分批顺序等正常推进中的取舍委派给 Worker。事件满足相应条件，或既定分支不足以处理异常时，运行时按当前 Assignment 唤醒负责人。

控制关系与信息关系

工作运行时先登记输入和来源，按可信标识、当前绑定与规则判断投递路径。主会话自然语言随后交给 Router 理解。已关联的外部回执和观测变化按原 Operation、Task 或有效 Goal 匹配。Router 和 Worker 提交工作决定，运行时校验范围、权限、版本与预算，再保存任务修订、分配或待执行操作。工作运行时是负责持久状态、确定性编排和 Agent 调度的程序机制。Router 与 Worker 是负责语义判断的两个 Agent 角色。

能力执行从运行时取得受控操作，通过适配器与外部系统交互。结果按操作和任务关联回到运行时，相关观测与证据进入信息模型。运行时依据当前计划和有效证据推进任务；需要判断时，上下文机制组装新的事实与待决问题交给 Worker。

信息查询与状态修改使用不同的责任路径。上下文、工作台和报告可以读取同一任务或资源的查询视图；发起修改则必须回到对应状态的管理入口。查询缓存和摘要保留来源与新鲜度，不获得独立改写事实的权力。

工作台直接读取工作运行时的进度和信息模型的对象视图，无需为每次浏览启动 Router。对象字段、指标、关联与可见动作由同一发布模型和查询定义解释。页面上的部署、复验、维护等动作进入工作运行时；模型定义草稿提交领域模型目录，经验证及发布身份核验后生效。

资源查询由信息与上下文解析对象、数据绑定和查询约束；需要访问外部后端时，把已登记的 QueryPlan 交给能力执行与治理中的只读查询执行器。该执行器位于图中的“执行网关与适配器”，核验当前读取权限、连接能力、必需过滤与预算后执行，返回实际数据与覆盖情况。内部元数据查询可以直接完成。查询结果沿只读请求返回给请求方，附来源、时间、覆盖和缺失项。用于判断或验收的结果按证据规则另行固定。执行或测试产生的效果观测和测试材料经信息模块核验后登记为事实或证据，状态回执按原 Operation 回到工作运行时。诊断任务内的查询保留 Task/Run 关联，普通只读查询无需创建 Operation。

V2 调用关系与感知运行方式

V2 架构图用颜色贯穿完整业务链路。实线表达请求或触发，虚线表达结果或回执。审批从准入提出请求、经网关和运行时送工作台、接收用户决定到重新准入，全程采用玫红色。采集与 NHC 检查全程采用青色，查询往返采用蓝色，动作执行采用橙色，任务协作采用绿色，上下文采用紫色。共用接口按业务用途分别画线。设计页可以选择单条链路，其他链路淡化显示。审批完成后继续原执行链路，执行结果仍关联原任务。

运行时保存工作计划与触发配置的关联、工作事件订阅和所属 Goal / Task。周期检查计划及其调度器的内置或独立服务实现尚待确定。用户通过自然语言委托 Router，Worker 在任务授权内提出计划或调整建议，明确的工作台配置请求直接交运行时。运行时核验来源、范围、预算和当前修订后提交计划，需要确认时先进入审批。调度设施按已生效配置处理到期项，发布可恢复的触发事件，由运行时决定创建或关联哪项工作。暂停、取消、目标到期和重启恢复统一使用这份持久状态。

“订阅”包含两种归属。工作事件订阅描述某项 Task / Wait 等待什么事件、哪些资源变化应触发有效 Goal，由运行时保存并匹配。外部来源订阅描述连接哪个监控源、接收哪类推送、如何建立或恢复连接，由共享连接适配服务维护。运行时保存需要这些数据的责任和订阅要求，适配服务保存实际连接与外部订阅标识，资源接入服务保存已提交批次和接入水位。

工具是可调用的能力接口，服务是持续运行的执行组件。一次 NHC 检查、读取监控、建立或撤销来源订阅可以暴露为工具或管理 API，经网关受控调用。SNMP / Webhook 接收器和持续订阅连接由常驻适配服务维持，建立配置请求结束后仍可持续接收事件。服务启动时读取已生效连接配置，按状态重连和续接，接收的观测经网关路由到资源接入服务。运行时根据已经接入的事件匹配工作责任。共用来源的订阅调整需核对仍有效的使用责任。

运行时拥有工作状态与调度控制，包括计划生效、触发去重、任务分配、Wait、审批、正式提交与恢复。后台定时扫描可以由进程内调度器或外部调度设施承载，运行时仍核对持久计划和执行资格。共享适配服务负责具体协议、连接、凭据使用、主动调用和被动接收。源端游标与接入水位按适配和入库契约维护，运行时保存的是任务触发位置与等待状态。

NHC 在当前方案中表示主动轮询检查。周期计划到期或用户要求临时检查时，运行时组织检查批次并登记所需执行，由共享 NHC 工具主动检查目标节点，结果通过网关进入资源接入与原工作记录。运行时记录本次完成、失败、超时和下次调度时间。SNMP Trap / Inform 与 Webhook 属于外部主动推送，由共享适配器中的常驻接收器承接。

共享适配器提供 MCP、原生 API、SNMP 和 Webhook 接入。网关按调用用途核验身份、范围和资格，将观测送资源接入服务完成去重、身份解析、质量与覆盖校验，持久登记批次后确认水位。连接、协议实现和凭据由能力执行与治理统一管理。周期检查、Worker 临时查询和 Task 操作复用同一套连接与适配器。

工作台有两条明确入口。自然语言委托、跟进和解释请求由 Router 理解，再提交工作决定。按钮命令、采集计划配置和结构化审批决定直接进入运行时校验。运行时直接向工作台提供待审批事项与操作结果，Router 负责对话说明和需要语义澄清的事项。

准入与资源协调返回允许、拒绝或需要审批。需要审批时，经网关交回运行时，运行时保存待审批事项及受影响的 Operation / 计划 / Skill 提案，并投递工作台。审批事项固定请求 ID、版本、对象范围、动作和参数，以及所需的授权或确认内容。工作台返回可信用户身份、审批事项 ID、对应版本及允许或拒绝决定。运行时核验审批资格与适用性后保存决定，再安排准入复核和续接。参数、范围或版本变化后重新判断审批适用性，资源占用与事实前提仍由最终准入校验。已有有效授权的动作按既定策略执行。

Worker 通过资源查询工具调用统一资源模型的查询服务。内部事实直接返回，需要监控或日志后端的实时数据时，查询服务生成 QueryPlan，调用网关内的只读执行器及连接适配器，再将返回数据与来源交回 Worker。运行时负责上下文装配和流程推进，也可以为既定步骤发起查询。V2 的蓝色调用链以 Worker 为发起者展示，流程查询复用同一查询入口。

集群运维以事件驱动工作推进。资源变化、作业回执、定时到期、用户修订和人工反馈进入运行时，先持久保存并去重，再匹配有效 Goal、Task、Operation 或 Wait。运行时结合当前状态、前置条件、规则版本和授权，决定执行动作、继续等待、委派 Worker 判断或交 Router 协调。事件发生后也可能只更新事实，具体推进由这些条件共同确定。

运维事件与状态规则定义触发条件、状态转换、步骤依赖、验收和外协升级条件。Workflow / Step 保存一项工作的组织关系与推进位置，部署后测试等依赖仍需满足。并行、重试、局部复验和人工等待按各自的事件与当前状态续接。运行时提交状态变更及后续投递，执行产生的新回执再次进入这条处理链。Worker 的决定提交后形成正式工作变更，随后仍由运行时按规则推进。

能力执行与治理接收运行时登记的 Operation，或者查询服务生成的外部只读请求。图中的运维事件与状态规则模块提供领域规则，事件受理和实际调度统一归工作运行时。

工单适配器作为工具注册到执行网关。Worker 提出开单、更新等动作，或已生效流程命中外协规则后，由运行时登记操作，再经网关准入并调用工单工具。工单工具调用外部工单系统，返回工单 ID，并将可信回调或查询到的人工反馈经网关关联回原 Operation / Task。运行时匹配 Wait，需要判断时唤醒 Worker，工单关闭后按原任务的恢复条件复验。

执行宿主接收运行时投递并保存送达、取入记录，通过运行时的上下文接口持久保存检查点。运行时、宿主和查询服务都带当前身份、工作引用与权限调用所属入口。

3 统一工作模型

Goal 与 Task

Goal 表达希望达到或持续维持的结果，例如完成一批节点交付，或持续负责一个集群的健康。它记录范围、成功或维持条件、预算、有效期、触发和停止规则、通知方式。简单的一次性工作可以直接建立 Task；持续责任由 Goal 管理触发规则，每次有意义的执行形成有界 Task。

Task 是能够分配责任、执行、等待和验收的工作单元。接受任务时形成工作契约：要交付什么、作用于哪些对象、受哪些限制、如何判断完成、失败后如何处理。按任务类型补充目标配置、资源占用和执行窗口等要求，普通任务无需填写运维专有字段。

一个 Task 至多有一个父任务，父子关系表达工作归属、预算分配和成果汇总。依赖关系单独表达执行前提，可以引用其他任务的成果，但不产生第二个生命周期负责人。运行时拒绝循环依赖。

需要独立责任、调度、并行、上下文或验收边界的工作才拆成子 Task。紧密关联的机械步骤由流程 Step 表达。父任务需要定义哪些成果必需、哪些可选、能否接受部分结果，以及局部失败后的处理方式；子任务全部结束不自动等于整体交付成功。

对象 生命周期与关系

Workflow 的定义提供可复用的执行步骤与条件，Task 保存本次采用的版本和实际推进状态。计划可以声明在什么事件和前置条件下由 Worker 选择下一步，以及可选择的范围、约束和超出范围时的协调路径。Worker 提交决定及依据，运行时复核 Task / Workflow 修订、当前分配、授权、预算和相关资源与证据版本后保存计划或操作。若依据已经变化，先刷新并按现行条件继续。已执行的步骤及其依据保留。流程定义、执行实例和会话历史不混为一份可随意改写的内容。

确定性步骤可以在无活跃 Run 时由运行时和执行能力推进。其过程仍有 Step 与 Operation 记录。Agent 发出的调用则同时关联实际 Run，便于追溯当次判断。持续执行依赖这些持久对象，模型无需一直在线等待。

暂停是阻止继续推进的控制意图，独立于执行阶段；暂停不能抹去原来等待什么。取消首先阻止新动作，再处理已发出的操作和未释放占用，不能用一个取消标记宣称外部工作已经停止。

未完成任务可以在有效授权内修订，修订保留要求、计划和验收条件的版本。同一交付目标的后续修订沿用原 Task，产生新的 Run、成果和验收版本，原验收记录仍绑定原成果；独立目标、不同责任范围或新一轮周期实例才创建关联 Task。取消后的重新委托需要显式受理，不能由晚到回执自行恢复。失败任务的显式重试可以建立新的 Assignment 和 Run，是否重新执行外部动作仍以 Operation 核对结果为准。用户可以在同一对话中持续修改成果，无需重述已有背景。

输入归属与持续触发

Event 保存输入来源、可信身份、时间、原始内容引用及关联标识。Thread 保存渠道中的讨论关系，一个 Thread 可以涉及多项工作。Subscription 决定哪些任务能接收相关上下文；触发规则决定在何种条件下恢复或产生工作。

运行时依据输入类型、可信身份和已登记的关联记录先匹配投递路径。路由规则决定由谁接收，授权规则决定接收方可以执行哪些动作。

通用模型预留任务专属跟进。只有入口有明确的跟进投递约定、消息命中可信任务绑定，且任务与负责分配有效时，运行时才可直接续接当前 Worker。仅作上下文的订阅用于供任务读取材料。当前尚未为 ClusBot 任务专属会话或飞书话题定义这项投递约定。语义相似度可用于查找候选，明确关联或订阅本身也不扩大操作授权。

输入事件、执行意图、Task 和 Operation 分别去重。一个事实可以合法影响多个任务，重复收到该事实不应反复创建相同操作。事件接收先持久保存，再匹配等待与触发规则；匹配位置可回查，避免结果早于等待登记时丢失唤醒。

周期工作、状态收敛和持续监测都绑定有效 Goal 或明确的授权责任。到期、停止、预算不足或没有需要处理的新变化时，不应无限产生工作。连接某个应用、记住用户偏好或订阅一段讨论，本身不构成持续行动授权。

4 统一资源与证据模型

模型定义与统一读取

“统一资源与证据”内部承担领域模型目录、资源身份目录、事实与关系管理、数据查询与溯源、领域判定与影响分析、证据管理六项职责。模型定义描述类型、字段、关系、数据集、存储与方法绑定及展示规则；运行实例保存实际资源与事实。工作对象、故障、知识和方法通过 ObjectRef 关联查询，各自的状态修改继续由原管理入口负责。

模型变更以 ModelChangeSet 保存基准版本、差异、样例验证和影响清单。目录核验发布资格与基准版本，发布完整不可变的 ModelPackRevision 并切换发布指针。查询、适配器、上下文和工作台按版本加载；未完成的迁移和投影明确显示水位。模型发布不直接改变设备状态；涉及 Skill 内容或行为的变更仍须用户明确确认。

查询遵循“定位对象 → 发现数据与方法 → 固定对象上下文和绑定 → 准备 QueryPlan → 执行受控读取 → 返回数据及来源”。计划与数据在结果信封中分别标识，数据注明当前/历史时间、采用版本、覆盖、截断、缺失来源和新鲜度。高频指标和完整日志留在对应后端；用于判断和验收的材料按需固定为证据。

身份 属性与关系

Resource 表示工作所作用的稳定对象。其通用结构包含对象类型、所属范围、稳定标识、外部系统映射、属性结构版本、来源、时间和访问要求。名称、地址和展示位置可以变化，任务与历史证据仍通过稳定身份关联。

对象关系也保存类型、来源和有效期，支持当前关系与历史关系查询。目录负责身份和映射，各领域数据提供方负责具体属性与关系。存在身份冲突时保留候选并核对，不能凭名称或地址相似度直接合并。

统一引用用于 Resource、Task、Operation、Artifact、Evidence、Memory 和 Skill，但各对象保留自己的语义与状态。引用至少定位对象类型、所属范围和稳定标识，需要重现历史依据时再指定版本或快照；引用本身不授予读取权限。

资源选择条件与本次实际集合分别记录。任务可以按条件寻找资源，开始执行后必须保存实际使用的对象及相关版本。后续查询结果变化不应悄悄改变执行对象。涉及多个来源时保留各自版本与采集时间，不将不同系统的版本号比较大小，也不假定快照天然对应同一时刻。

目标 观测 判定与执行条件

资源模型允许各领域定义四类相互关联的信息：目标状态说明希望达到什么；实际观测说明看到了什么；领域判定说明规则与证据支持的结论；执行条件说明某个动作当前是否可以开展。

目标状态关联提出它的 Goal、Task 或有效策略，记录作用范围、版本与有效期。同一对象存在冲突目标时按明确规则解决，不能无条件采用最后一次写入。目标配置版本与资源记录版本不同，一次新的观测不会自动改变目标。

运行时保存 DesiredBinding，并将当前有效绑定、工作修订和规范引用提供给资源模型；领域规则解析 EffectiveDesired 后与实际事实比较。Condition 使用 True、False、Unknown 表达有依据的满足、不满足和未知。针对某次动作的 EligibilityDecision 则结合操作者、动作参数、目标与影响集合、当前目标修订计算 Allow、Deny 或 Unknown，并返回阻塞原因与依赖版本。

资源协调授予的 Claim 只证明相应使用条件已经落实。最终执行资格还需执行网关核对当前任务授权、身份、领域判定、事实时效和占用；验收提交也重新核对必要版本。查询投影、页面缓存和过期的准入解释不能直接作为执行许可。

观测保留来源、发生或生效时间、采集时间与系统获知时间。领域判定关联所用观测、规则版本和适用范围，能够表达未知。执行前综合判定、授权、资源占用和事实新鲜度；未知、过期或失效的信息不默认满足条件。通用模型承载这些关系，具体状态维度与判定函数由领域定义。

Artifact Evidence 与验收

Artifact 是文件、报告或其他可交付成果。Evidence 是支持某项判断的可追溯材料，可以引用 Artifact、原始观测、外部记录或 Operation 结果。证据记录其来源、适用对象与版本、时间范围及判断用途，不能只保存模型给出的结论。

Task 的验收要求关联需要满足的条件和证据。工具返回成功只证明其报告的执行结果；目标是否实现，需要查询或验证实际效果。涉及多个资源时，验证覆盖本次实际集合与整体要求，局部步骤成功不替代整体验收。

验收结论与历史结果固定当时依据。资源或规则后来改变，不追改过去曾经完成的事实；系统判断旧证据对当前操作是否仍适用，需要时安排新的验证工作。

联机测试固定 ResourceSetSnapshot、成员角色与 SnapshotManifest，EvidenceUse 单独说明历史材料对当前契约的适用性。验证门禁按“要求 × 对象/对象组”检查覆盖、缺失和失败，返回 AcceptanceRecord 及采用的 Task 修订；交付还需独立核对业务接收及投递结果。

变化传播与有效性

任务、操作、判定和派生知识记录对资源、规则与证据的依赖。事实或规则变化后，领域规则说明哪些结论可能受影响，运行时标记相关工作需要复查，上下文机制更新下一次执行的依据。该机制同时服务资源变化、用户要求修订和知识纠正。

复查需要区分与当前任务无关的变化、仍可复用的证据和必须重验的部分。变化不能被摘要隐藏，也不意味着全部结果统一失效。关键动作在执行入口重新检查相关条件，当前事实查询与历史解释使用各自适用的版本。

事实、关系、目标或规则提交后发布可恢复的变化事件，影响分析按依赖重算 Condition、EvidenceUse 和待复查范围；定时到期与读取时检查处理没有新事件的失效。事件与恢复机制接收已解释的变化和受影响工作，在有效 Goal 下按偏差 episode 关联或创建有界 Task；重复采样不逐次唤醒 Agent。

Operation 提交与效果确认

每个有副作用的能力调用形成 Operation，至少关联所属 Task 或 Step、发起来源、稳定标识、目标对象集合、提交参数及版本、授权依据、前置条件、占用要求，以及查询、重试、取消和验证方式。执行时仍检查当前授权，历史授权快照只用于解释当时依据。

运行时先持久保存操作意图，再安排外部执行。状态变更与待执行动作登记通过事务或等效的可恢复机制衔接，避免状态已推进而动作丢失。执行网关核对操作资格和条件后调用适配器，将外部作业标识、回执与错误关联回原操作。结果与外发消息也保留可恢复的投递记录。

网关完成准入核验后，向运行时请求登记本次派发开始。运行时在同一 Task 的控制事务序列内复核版本和当前资格，登记本次尝试后才允许网关调用外部。暂停先提交时，拒绝尚未开始的尝试。派发开始先提交时，暂停保留该次在途或结果待核对的尝试，回执区分已拦截与仍待核对的范围。外部调用在本地事务之外，开始登记后若进程中断且实际结果不明，沿原 Operation 查询和对账。后续新尝试仍须通过当前资格与安全重投条件。

正式交付后的结果通知另有待发送记录，保存稳定通知 ID、已核验的接收对象、正式结果引用与渠道回执。临时失败时按原通知重试，目标不可达或重试耗尽时转待决，保留正式验收和交接结果。交付契约要求的业务接收仍由 DeliveryRecord 核实。 DeepSeek Outbox 实现

同一操作的重复投递与恢复复用身份，不因此产生新的工作意图。目标或参数实质变化时保存新的 Operation 并关联前序，不能追改已经提交的请求。重试是否安全取决于外部能力的实际契约；持久队列本身不保证外部系统恰好执行一次。

响应丢失时，外部操作可能尚未开始、正在执行或已经完成。恢复者先查询或重连原作业，只有确认未执行或具备安全幂等条件才重新提交。无法确认时保留待核对状态及相关资源限制。外部执行结束后还需按要求验证效果，完成回执不自动等于 Task 验收通过。

等待 恢复与资源占用

等待记录说明正在等哪个对象或结果、如何确认、何时恢复、何时复查、超时如何处理，以及依赖的检查点。运行时保存事件位置并回查已发生结果，避免先到的完成事件被遗漏；同一等待只触发一次有效推进，重复事件用于补充或合并证据。

恢复首先检查任务是否仍有效、是否暂停或取消、当前授权与执行资格是否成立，再核对未确认操作和资源占用。资源或验收要求变化时先判断影响。能够确定性推进的部分直接继续；需要 Agent 判断时，装配当前上下文并建立新的 Run。

占用记录属于持久 Task 或 Operation，包含实际资源、使用方式、持有者、有效期、续期与释放条件。运行时提出申请并记录关联，资源协调能力决定是否授予和释放。Agent 执行槽与节点、设备或外部作业的占用分别管理，等待释放推理容量时不自动释放正在使用的实际资源。

执行者失联或租约过期不能证明外部操作已经停止。重新分配后需要核对占用与外部执行，再续接、释放或保持阻塞。任务取消仍保留必要的结果核对和释放责任；只解除该工作持有的限制，其他有效占用和人工限制保持各自归属。

恢复以已存在的 Operation、外部作业引用和 Wait 为入口。只读核对仍可在 Task 暂停或取消后继续，新的业务推进则必须服从当前控制意图。Task 有效而旧 Assignment 失效时，运行时在对账后改派并更新代际；需要新判断才建立新 Run。同意图安全重投只新增原 Operation 的投递尝试，重新核验当前资格和占用，不重复创建意图或授予 Claim。

修订 暂停与执行者更换

用户补充事实时，由范围内任务负责人判断其影响；目标、范围或跨任务优先级变化由 Router 协调，经运行时形成修订。修订记录受影响的任务、计划、验收与权限版本。尚未发出的旧动作可以撤销，正在执行的动作按能力契约处理，迟到结果只有仍满足当前要求时才能用于完成判定。

改派时使旧 Assignment 失去控制当前 Task 和发起新动作的资格。旧结果保留为历史证据，是否复用由当前负责人判断。执行权标识只能约束实际检查它的入口；外部设备或系统不支持此机制时，需要幂等、状态核对或动作串行化防止冲突。

暂停阻止新推进，正在发生的动作按能力支持程度停止或运行到可中断点。取消不能承诺撤回已经发生的外部效果。取消一个周期的 Task 与停止持续 Goal 分别处理；停止 Goal 关闭其后续触发和所属未完成工作，并核对在途效果，不影响其他目标通过引用使用的成果或仍有效的责任。

监督 预算与异常处理

任务调度根据优先级、依赖和容量推进，并避免低优先级工作无限等待。子任务、验证、重试与经验整理都计入所属预算，拆分不能重置额度。调整优先级不等于可以中断不可中断的外部动作。

运行时监督处理无心跳、超时、等待过期、重复触发、重试耗尽和预算异常。需要判断目标偏离或方案质量时，安排有边界的审查 Task，由 Worker 返回结论，再进入原工作修订流程。审查角色不建立另一条指挥链。

异常处置区分可在当前授权内修正的问题、需要新证据的未知状态和需要用户决定的取舍。系统保存已完成部分与未解决事项，向用户给出具体影响和可选处理方式。持续优化具有成功条件、复查条件和停止条件，不能因仍有改进空间而无限生成工作。

模型暂时不可用时，事件接收、状态记录、结果匹配和既有确定性步骤仍可在原授权与条件成立时运行。需要新判断的部分等待恢复或人工处理。该边界保证长期工作不依赖一次不间断的模型会话。

6 持久上下文与长期知识

信息的职责分工

ClusBot 将正在做的工作、已经观察到的事实和从经历中形成的知识联系起来，同时保留各自权威来源。Task 和 Operation 说明工作进行到哪里；资源与观测说明当前及历史环境；Evidence 支持结论；Memory 保存值得复用的经历、知识和偏好；Session 保存对话连续性。

上下文是面向本次 Run 装配的工作视图。它从上述记录读取所需信息，标明来源、版本、适用范围和未确定部分。Session 可以压缩或重建，任务的继续依据仍然存在；记忆可以更新，资源当前状态和工作进度仍由原管理方维护。

持久上下文以 ContextManifest 记录采用的对象、任务、模型和方法版本、历史执行快照、当前查询结果、未知操作、占用及证据缺口。结构化 Incident/Hypothesis、支持和反驳关系及诊断状态由 Worker 提交工作运行时保存；会话中的推理草稿与检查点保存在上下文中，并引用正式记录。上下文压缩或重建不能丢失故障调查的权威状态。

ContextManifest 的统一维护入口位于信息与上下文模块。会话记录器随用户消息、模型响应和工具结果追加 Session，清单在重要进展、等待、暂停、交接、压缩及恢复时形成新修订，记录消息覆盖位置与需核对的事实。每次 LLM 请求可复用已装配材料并加入后续消息，资源查询按调查需要、依赖变化和新鲜度执行。暂停先由运行时保存控制意图并生效，恢复时核对原操作与当前环境，清单装配完成后由运行时再次复核并启动 Worker。字段、维护责任、更新表和完整示例见统一资源模型设计第 10.2 节，对应维护与装配图和执行、暂停与恢复图。

知识机制采用经历、可修订知识与派生主题视图的统一组织方式，结合时间有效性、来源追踪与渐进披露。不同信息表示各司其职，共用对象与证据引用，不按参考产品分别建立几套记忆系统。

上下文装配与恢复

运行时向持久上下文发出装配请求；上下文读取权威记录并返回 ContextManifest。运行时在装配完成后再次核对当前工作修订、控制意图和执行资格，再启动或唤醒 Router / Worker，交付事件、工作身份及 ContextManifest。持久上下文负责材料组织与会话保存，不承担 Agent 调度。Agent 后续可按权限展开材料并保存检查点。

Router 常驻上下文包含用户当前表达、有效约束、目标与任务总览及需要协调的变化。Worker 上下文围绕具体 Task 展开：

依据 装配内容
工作依据 当前 Goal、Task、计划、验收条件、授权、预算、负责人关系和所用 Skill 版本
资源依据 实际对象集合、相关属性与关系版本、新鲜度、占用及外部业务状态

恢复使用当前任务和授权重新核对操作、资源与证据，再形成新的上下文。旧快照用于解释过去为什么这样做，新事实用于判断现在能否继续。重要变化到达活跃 Run 后，应在下一判断或动作边界处理并记录采用的版本。

例如测试等待期间驱动版本变化，系统仍保留测试启动时的配置，但恢复者需要看到当前配置及变化影响，决定该结果能否用于现在的验收。只保存“测试已启动，等待结果”不足以恢复这项判断。

本轮输入与恢复清单

Manifest 除工作、资源与方法引用外，保存实际输入事件、材料和工具回执修订、记忆路由/条目/策略版本、压缩来源、预算及省略原因。每轮复用仍有效的静态材料并补入新输入；权限撤回、记忆删除、Task 修订或关键事实变化时重核适用性。原清单不改写，恢复者根据正式记录建立新清单。

当前要求、授权约束、未知副作用、未解决问题和成对工具调用/回执不得静默丢弃。可选历史按相关性、时效和成本裁剪；必需内容超限则拆解或请求更小材料。Manifest 说明使用了什么，Checkpoint 说明执行恢复位置，Task/Operation 说明真实工作状态，三者不能相互替代，也不要求持久化模型隐藏思维。

内部任务、路由、记忆更新和控制决定使用结构化数据，用户报告继续支持 Markdown。结构验证之后仍检查身份、权限、引用存在性、当前修订、预算和业务含义；可解析 JSON 不等于事实正确或获得执行资格。

经历 知识与主题视图

经历记录一项工作的条件、主要动作、结果、反馈和原始证据引用，保留成功、失败及未确定结果的区别。完整日志和大文件作为证据材料保存，经历只组织必要信息，避免将所有原始数据重复写入记忆。

知识记录表达有来源、时间范围和适用条件的事实、关系、偏好及整合经验。事实生效时间与系统获知时间分别记录，以支持当前与历史查询。对象的权威事实变化时更新引用或派生知识，不能由一段记忆摘要覆盖资源来源。

主题视图围绕常见问题维护精简内容，例如某集群的主要风险、某类故障的已知证据或用户的有效偏好。它由知识与证据派生，注明覆盖范围与新鲜度。来源变化后重新整理或标记陈旧，刷新未完成时补查来源。

有新证据或达到整理条件时，由有预算的 Worker Task 提取候选经历与知识，检查重复、冲突、适用条件和反例，再按记忆更新规则发布。多条材料源于同一信息时不能当成独立证据累加；相关性不能自动升级为根因。复杂推断由当前任务负责人判断，记忆维护不改变目标或执行权限。

工作上下文、经历、知识、方法经验、用户与角色信息、未来意图可以作为检索分类。未来承诺的真实状态仍在 Goal 与 Task，已发布方法的版本仍由 Skill 治理维护，分类不产生额外状态系统。

检索 共享与维护

检索先按用户、工作空间或项目、任务和角色私有范围检查权限，再结合对象、时间、关键词、语义及必要的关系寻找材料。结果提供摘要、适用条件和来源路径，Worker 可以从主题概览展开到具体证据，也可以直接读取用户指定的原文。

常驻上下文保留当前目标、明确约束和必要状态，详细日志与历史按需展开。预算紧张时优先减少重复、陈旧和低相关内容；关键权限、未完成动作、重要错误及等待条件从结构化记录恢复，不只依赖压缩摘要。目录、标题和引用同样遵守访问边界。

用户纠正形成带来源的新版本；Agent 推断保留推断性质，按影响程度决定是否进一步核验。冲突知识先比较对象、时间、方法与证据，允许不同时期的事实并存。共享更新检查基准版本，避免最后写入覆盖所有先前结论。

纠正、删除或作用域变化需要同步处理索引、缓存和派生视图，避免旧摘要重新出现。历史任务证据按独立的保留与访问规则处理，活跃任务依赖的必要材料在处理引用关系前不能盲目清理。原始证据不可用时，查询结果明确说明这一限制。

信息与上下文内部的状态归属

V2 的信息与上下文大框内部按事实、经验和装配分工。资源服务拥有身份、观测、关系和证据；记忆管理维护偏好、情景、知识、簇和策略版本；上下文装配保存 Manifest 与检查点并读取前两者。运行时继续拥有尚未完成的工作。各入口可在同一 Go 进程、同一 SQLite 中实现，图上的逻辑分工不要求新增数据库或独立服务。

Memory Router 是该模块内部的经验选择机制，与面向用户/工作的 Router 不同。需要模型辅助时使用有界调用或已有 Worker 角色；不引入新的管理 Agent 层级。已发布 Skill 属于能力治理，记忆只保存方法候选、来源及使用关联。

经验路由与簇状态

采用 Routed CL 的“选择经验共享边界与表示机制”思想，但首批只实现可审阅的情景检索和知识条目两种表示。HR/HDE/PES 数值系统仅在出现稳定字段、单位、反馈和对应评测时作为插件试验。记忆簇是经验分组，不能与物理 Cluster 混名。

Memory Router 输入任务语义、环境/工具版本、输出契约及可读簇摘要，返回 reuse/create/no_memory 提案；程序校验访问范围和受支持机制。先用规则确定明显领域，只有模糊情况调用模型。没有足够证据时允许不用经验；不能只按 Markdown/JSON 输出形式分簇，也不能每次轻微变化都建新簇。

选中簇后先按权限、适用环境、时间、状态和来源过滤，再做关键词/语义检索与排序；检索失败降级为当前事实与工具调查。一次工作修订中的主簇和更新策略固定；跨领域子任务单独路由。更改路由必须留新决定，旧轨迹不能因晚到结果写进新的簇。

更新由 Memory Manager 负责。来源事件/尝试族作为幂等键，按簇修订做原子提交；并发冲突重读后合并提案。LLM 可提出新增、合并、冲突或归档建议，不能自行把失败标成已验证成功。原始轨迹留在运行时/成果归属中，记忆存必要引用和允许保留的摘要。

记忆生命周期与效果评测

个人明确记忆按当前用户操作生效；自动抽取的新偏好先作为可确认候选。经验条目经历候选、可用、存疑、失效或归档。来源权限变化和删除要沿派生依赖传播到摘要、索引与 Skill 候选；已记录使用可以保留必要的审计引用，但不能把被删除正文重新送入模型。

保留、失效、降权与删除分别处理：事实已经不成立是有效性问题；条目不值得主动检索是效用问题；用户删除则是数据生命周期请求。合并不抹去反例，摘要不能成为自己的证据。个人“喜欢快速执行”不能改写操作审批、参数或日志规则。

内循环更新经验内容，外循环改进记忆管理策略。外循环先记录问题，再提出候选检索/写入/巩固规则，在隔离记忆分支上重放相同任务流，固定模型、工具环境和预算，对比无记忆、旧策略、新策略。考察任务成功、证据正确性、错误复用、保持/适应/迁移、成本与时延；记录“被检索、被纳入、被引用、经验证有效”的不同信号。仅有引用或模型自评分不能证明因果收益。

策略发布使用不可变版本和回滚；先离线评测、后有限范围使用。权限与准入是硬约束，不进入可优化奖励权重。初期不做在线权重训练，也不让模型自主替换生产记忆架构。以上是 ClusBot 对 MCCL、Routed CL 等研究的工程取舍，具体对照见本文附录。

7 能力执行 Skills 与授权

能力目录与执行入口

工具和 MCP 提供能力调用接口，Skill 提供适用条件、方法与验证要求，Workflow 负责本次工作中步骤与状态的推进。三者可以共同服务一个 Task，各自版本和职责保持清楚，不因工具数量增加而创建同等数量的 Agent。

能力目录记录用途、输入输出、运行环境、访问要求、副作用、同步或异步方式、状态查询、幂等、重试、取消和效果验证能力。Worker 根据当前任务需要及权限查看目录，运行时与执行网关在实际调用时再次校验。支持 MCP 只说明接口形式，具体执行语义仍需能力契约说明。

只读查询执行器校验服务端登记的 QueryPlan、当前读取权限、来源连接、必需过滤、有效期与预算，再落实后端读取，返回带来源、时间、覆盖和对象标识的数据；不能将查询计划当成已取得的数据。读取也遵守实际通道和资源兼容约束。有副作用的调用通过 Operation 执行，涉及资源使用时核对占用。外部报告和消息发送同时检查接收对象与允许披露的范围，读取资料的权限不自动授予对外发送权限。

ConnectorBinding 固定采集来源、共享适配器与映射版本、责任范围和凭据引用。工作运行时的触发调度管理周期和工作事件订阅，共享适配服务管理外部来源连接、协议调用和接收。资源接入服务按 SyncBatch 校验并提交观测及质量信息，确认后推进水位。采集失败与设备异常分别表达。来源连接和凭据由执行侧管理，模型与上下文只暴露授权后的元数据。

来源账号通过明确绑定对应用户身份，不能依据名称相似度建立信任。外部网页、日志、工单和工具返回中的文本按数据使用，不能修改执行权限。并行任务的文件、会话、凭据和副作用边界需要隔离，具体执行环境后续选型。

Skill 使用与版本

Skill 目录区分候选、已发布与历史版本。新任务按条件选择允许使用的方法，记录其版本；在途任务不因新版本发布而静默切换。实际动作仍受当前任务授权约束，方法可用不意味着其中每个动作在当前环境都获准执行。

任务结果关联使用的 Skill 版本和证据，以便比较适用性与效果。发现方法失效或执行条件不成立时，当前 Task 可以停止或等待处理；Skill 的全局启停、修订和回退仍走明确的变更确认流程。回退方法版本不承诺撤销已经发生的外部效果。

Skill 增长与变更治理

经验默认先进入经历、案例或方法证据。相同方法的不同参数通过参数或引用材料表达，重复案例不持续扩张 Skill 正文。存在稳定复用价值时优先修订已有方法，只有现有能力不能覆盖且具有独立价值时才提出新增。

比较 Skill 时检查目标、适用条件、输入输出、所需能力、依赖和反例。名称或语义相似度用于找候选，不能决定自动合并。互斥方法需要明确边界和处理方案，不能以最新版本或相似度最高者直接替代其他方法。

所有 Skill 变更必须主动通知用户，展示具体方案并取得明确确认后执行。 确认前，候选方法不进入可加载的 Skill 目录，也不改变已有启用状态。此要求适用于新增、修订、合并、替换、启用、停用、回退、删除，以及影响行为的适用条件和优先级调整：

  1. 形成具体提案，说明目标 Skill、基准版本、差异、理由与证据、适用范围、冲突、依赖影响和验证方式。
  2. 主动通知用户并等待明确确认。仅列入内部清单、已读、未回复或超时都不构成同意。
  3. 将确认绑定具体提案。执行前核对基准版本，内容或影响改变时更新提案并重新确认。
  4. 按确认范围执行和验证，再记录发布状态与结果；验证失败保持已有发布状态，后续调整按确认范围处理。
  5. 向用户反馈执行结果，保留历史版本及其任务引用。

结构化确认必须绑定可信身份、提案 ID、候选版本和具体范围，可由运行时与治理确定性处理。自然语言回复由 Router 解释作用范围，含糊时继续澄清；模型解释本身不能充当授权。候选内容、基准或影响变化时生成新提案版本，旧确认失效，新版本重新经过运行时、Router 和工作台主动通知用户。等待与澄清保留持久状态，不以重复通知或超时推进发布；验证通过后仍须在发布边界复核基准与确认适用性。

普通记忆写入、流程模板或其他工具路径不能绕过上述规则。使用已有有效 Skill 与修改 Skill 分别处理；能力治理入口负责检查确认，不能只依赖 Agent 自觉遵守。

反馈与行为变化

用户事实补充与评价可以按规则进入上下文和记忆；目标修订进入工作运行时；方法变更进入 Skill 提案；影响自主行为的运行策略按其变更规则与有效授权处理。不同变化保留各自依据与版本，不能将新的操作规程改称记忆来规避确认。

优化以任务质量、返工、故障处置效果、成本和用户打扰程度衡量。记忆条目、Skill 和 Task 的数量不代表进步。模型权重训练不属于本阶段设计。

8 集群交付与运维设计

领域定义与通用机制

集群运维将前述工作、资源、证据和能力模型具体化。用户交代交付或维护责任后，ClusBot 使用同一套 Router、Worker 和工作运行时推进，领域规则提供判断与执行所需的专业含义。

通用机制 运维领域定义 作用位置
Resource 与关系 集群、节点、部件、拓扑、资源池、作业及其映射 资源目录与领域数据提供方
目标、观测、判定与执行条件 配置目标、健康与验证状态、业务占用、可交付或可维修条件 信息模型与领域判定规则
Task、Workflow、Step 与验收 部署配置、测试验收、故障处置和报告等工作的模板与交付要求 工作运行时及负责工作的 Worker
Operation 与资源占用 BMC、部署、测试、监控、工单和调度器操作，节点组选择与维护预留 能力执行及领域资源协调能力
Evidence、Memory 与知识关系 配置快照、测试结果、故障假设、处置案例和适用性经验 证据管理、上下文与知识维护

这些定义构成 ClusBot 的运维能力。既有工具、流程和业务系统提供实际执行或数据，ClusBot 负责将它们组织成可持续承担的工作，并对结果保持核验与反馈责任。

资产与节点状态

资产发现将来自 BMC、带内系统、网络和部署系统的线索归并到稳定资源身份。节点、BMC、加速卡、网卡、交换机端口、资源池与业务作业保持各自类型，通过组成、连接、归属和占用关系联系。发现信息不足或身份冲突时形成核对工作，不能按 IP 或相似名称自动认定同一设备。

配置与拓扑需要同时支持当前查询和历史重现。一次验收使用的 OS、驱动、网络和连接关系随证据保存引用，后续换线、换卡或配置更新不能切断过去结果与当时环境的关系。

节点的生命周期、健康、验证、维护和分配分开表达。已交付属于生命周期事实，故障属于健康变化，业务占用属于分配事实，它们可以同时存在。BMC 电源状态、OS 可达性、链路和业务作业状态属于观测，不能全部压成一个综合节点状态。

领域规则根据观测形成 OS 就绪、硬件健康、配置符合、验证通过、调度状态一致等判定，采用 True、False、Unknown，并关联证据、目标版本和新鲜度。可部署、可测试、可交付、可分配或可维修是当前条件的计算结果，不再人工维护一套脱离依据的布尔状态。具体名称、状态枚举与阈值在详细设计中确定。

持续配置责任比较有效目标与实际状态，偏差出现时关联或产生已有规则允许的工作。重复观测不重复提交同一操作，过期观测先补查，冲突目标先解决归属与优先关系。一次性测试和调查按有界 Task 执行，不强制形成持续收敛目标。

节点交付与验收

交付工作以资源范围、目标配置、验收要求和授权为契约。运行时采用适用的版本化流程组织发现、部署、配置、单机测试、联机测试、验收和交接。批次、参数和流程已明确时可直接启动；范围或方案待确定时，交付 Worker 依据发现结果完成本次规划。哪些阶段拆为子 Task，由独立责任、并行与恢复需要决定。

运行时把观测或回执关联到原 Task、Step 或 Operation，再按当前计划和证据处理：

条件 下一步
规则已确定下一步 运行时直接推进，例如条件通过后开放后继，或按已授权规则补采、补测。
到达计划委派的取舍点，或异常需要新的判断 运行时携带当前上下文唤醒交付 Worker。Worker 在授权内直接决定选组、分批顺序、诊断或局部复验，提交决定和依据。运行时复核后登记并执行。正常通过与异常均可进入该分支。
需要改变用户已确认的交付范围、时限、验收承诺或追加授权 运行时记录待决与受影响的步骤，由 Router 协调并在需要时请用户决定。有效修订生效后继续原 Task。

例如两组节点均通过联机测试，已规定先交哪组时运行时直接推进。若契约允许 Worker 根据实时占用、拓扑和接收优先级决定先交哪组，则两组证据就绪后唤醒 Worker。选组结果进入正式工作记录，交付仍需通过验收、资源协调和外部接收核对。

部署与配置工具通过 Operation 执行，异步作业保留外部标识和等待条件。资源不能同时用于冲突业务或维护工作；执行条件与占用在实际操作前检查。局部失败保留已完成部分，相关依赖等待或按允许范围重排，父任务继续维护整体交付标准。

联机测试针对实际节点组及其环境。测试证据关联参与集合、硬件与配置、拓扑、测试方案、判定规则、基线、时间和原始结果。资源集合或关键配置变化后，依据影响规则决定复用或重验，单节点全部通过不能替代联机要求。

整体验收检查所需资源的覆盖、配置符合、测试结果及证据有效性；交付涉及业务调度器时还需核对外部系统中的实际可用状态。验收结论、交付成果和发送结果分别保存。交付 Task 成功后，历史结论固定；有效的持续维护 Goal 继续负责后续健康与变化。

资源分派与业务调度协同

任务调度负责何时启动 Agent 或推进流程，领域资源协调负责选择和预留实际资源，业务调度器负责业务作业的分配事实。运行时拥有可用执行槽，并不说明设备可用；本地记录了维护意图，也不证明业务作业已经排空。

资源申请包含目标类型、实际集合或选择约束、影响范围、使用方式与释放条件。占用可以覆盖节点、部件或节点组，兼容规则按操作实际影响定义。长期测试或维修等待时继续保留必要占用，不能因为 Run 结束而重新分派节点。

维护请求先登记意图并协调冲突工作。影响业务的维修只有在外部调度器阻止新分配、现有负载满足维护要求及其他前置条件成立后才能推进。修复验证完成后，只解除本流程持有的限制；其他故障、任务或人工隔离仍有效时保留。恢复分配还要核对外部调度器状态。

交接前先确认维修动作停止，将自身 Claim 转入 releasing 并撤销维修执行资格，随后以当前交接资格执行解除自身限制或恢复分配的 Operation。外部确认自身交接后才完成 released；不确定时保留交接和核对责任。修复、占用交接与约定业务指标分别核验，各 Task 按自己的契约完成并将剩余责任反馈 Router。

整个协同过程允许存在已提出维护、等待排空、修复完成但尚未恢复分配等中间情况。状态不确定或回执丢失时查询实际事实并保持必要限制，不盲目重试或宣布可用。具体排空、预留、资源选择、恢复与失败分支后续按实际调度器能力细化。

监控 故障与自愈

持续健康责任定义关注资源、监测条件、有效期、处置范围与通知方式。监控、NHC 和资产数据由共享适配器取得，经网关核验来源后送资源接入服务，在信息模块内完成去重、身份解析、质量与覆盖校验及观测水位登记。采集与入库由确定性程序完成。资源模型按规则生成变化事件，运行时匹配有效维护责任和现有 Task，需要诊断或选择处置方式时才唤醒 Worker。外部作业或工单回执按已登记的外部标识接回原工作。

Incident 保存症状、影响资源、故障假设、证据和恢复情况。处置 Task 保存诊断、修复与验证工作，可按责任边界拆分。一个故障可以关联多个资源、Task 和工单，工单关闭后仍按恢复条件核验效果。

工单用于把需要人工或外部团队处理的问题交给有责任的一方，例如硬件更换、现场核查或跨团队确认。运维工作流定义升级条件、等待条件和回执后的继续步骤，工作运行时持有原 Task、工单关联与 Wait。写入动作按受控 Operation 经过共享的能力执行与治理底座，核对授权、接收对象和可披露范围，由工单适配器创建或更新工单。适配器通过查询或可信回调同步状态和人工反馈，按来源及外部工单 ID 匹配原工作。外部工单系统负责工单的受理、分派、状态和协作记录，ClusBot 依据现有责任与验证规则推进 Task 和 Incident。

已知且适用的方法可以在有效授权及执行条件成立时用于处置；未知问题由 Worker 收集证据、提出并检验假设。修复操作通过统一执行入口，必要时先满足维护与业务调度条件。效果验证通过后再更新恢复结论和相关分配资格，失败或不确定时保留问题与限制并继续处置或升级。

故障上下文贯穿假设、支持与反驳证据、已排除原因、采取的措施和验证结果。知识关系组织可复用事实，故障关系表达症状、可能原因、措施与验证，资源关系描述实际组成与连接；三者共用资源身份与证据引用。相似案例可以提供诊断方向，修复后恢复正常也可形成案例，但根因是否确定仍取决于证据。

策略改进 报告与主页

任务与故障结果进入经历和知识维护，支持按硬件、配置、拓扑与方法版本比较效果。测试增减和监控频率调整由有界优化 Task 评估，提出适用范围、证据、版本、覆盖要求、评估指标和恢复条件，依照有效授权与变更规则实施。

强制验收、最低检测覆盖以及配置变化或故障恢复后的复验要求由领域规则约束。优化结合故障发现、误报与漏检、恢复情况、资源成本和覆盖率判断，不能因历史故障少就持续减少检测。涉及 Skill 变更时仍必须主动通知并取得用户明确确认。

周期报告由持续 Goal 的触发规则产生 Task；按需报告使用同一工作机制。报告记录查询时间、数据范围、指标口径、来源和成果版本，投递按接收对象与披露权限执行。生成完成但渠道失败时只恢复投递，发送结果未知时先核对。

工作台查询资源、目标、任务、故障、证据、成果和待决事项。用户可以要求生成适合当前问题的主页，系统保存视图定义及受控查询引用，按当前权限持续展示数据。页面发起执行请求时回到统一任务与操作入口，页面本身不维护另一份进度或资源真相。

交付与长期维护的协作闭环

以“完成一批节点交付，并持续维护其健康”为例，Router 将一次交付结果与持续维护责任分别记录，明确资源范围、验收标准、处置授权和通知要求。运行时安排交付负责人，信息与上下文提供资产、当前状态和相关经验。

运行时采用适用的交付计划并组织依赖与资源条件，执行能力完成实际部署和测试。计划待确定或到达已委派的选组、分批等决策点时，由交付 Worker 在授权内决定，运行时复核并登记。外部工作跨等待继续，结果回到原操作和步骤；配置或目标变化时，相关证据经过适用性复查再计入验收。整体条件满足后形成交付结果，Router 告知用户，工作台展示同一事实。

此后维护责任继续接收监控与配置变化。故障事件关联资源和 Incident，运行时形成或恢复处置工作，Worker 使用当前事实、交付证据和历史经验诊断。修复操作在资源与业务条件允许时执行，经验证和调度状态核对后记录恢复；处置经验进入知识，必要的方法改进形成待确认提案。

用户在任意阶段都可以追问、修订、暂停或停止相应责任。其输入作用于当前目标与任务版本，并在下一判断和执行边界生效。至此，用户要求、资源事实、执行效果、验证证据、经验和下一次工作在同一 Personal Agent 内相互衔接。

方法与角色治理 Hermes Skills、记忆更新、OpenClaw 多 Agent、NanoClaw 隔离。采用按需方法目录、可配置角色与上下文隔离；全部 Skill 变更主动通知并经用户确认，是 ClusBot 的明确约束。

论文机制与本设计取舍

下列“机制”是原文概括，“采用”及“限制”是对 ClusBot 的工程判断。每项只借鉴适用机制，不承诺引入相应软件栈。

UModel

UModel: An Agent-Ready Observability Data Modeling Method at Scale，重点读 III–IV 的对象、关系、查询和应用接口。

**机制：**以对象语义关联异构可观测数据、关系和能力，提供统一查询和 Agent 接口。

**采用：**延续已有领域模型目录、ObjectRef、两级数据绑定、统一查询信封与查询计划；把原始指标/日志留在后端，内部保存身份、关键事实和证据。

**限制：**UModel 并非完整任务运行时或学习系统；ClusBot 的授权、Operation、Claim、验收和持续责任仍自主管理。不直接假定其源码与当前本机工程兼容，也不因论文有图查询就新增图数据库。

Routed Continual Learning

Routed Continual Learning，重点读 §3、§4 及 Adapter 验证附录。

**机制：**任务开始时选择一个记忆簇及其固定库内机制，实例中选择保持不变，仅更新被选簇。Router 使用可见任务/输出格式与簇摘要，不能查看原始轨迹；实验没有学习其路由提示词。五种机制为 ICL、ReasoningBank、HR、HDE、PES。

**采用：**Memory Router 独立于任务 Router；任务规范先由入口/模板确定。固定本次路由和策略版本，原子读写簇状态；先实现情景/知识检索，允许 no_memory 降级。

**限制：**HR 的标量、HDE 的离散事件、PES 的实体测量各需匹配的数据与反馈，不是通用运维记忆的必选组件。按权限过滤、簇生命周期和删除传播是本项目补充；不声称论文验证了这些生产约束。

MCCL

Memory-Centric Continual Learning for AI Agents，重点读 §2 三轴、§3 生命周期与 §4 评测。

**机制：**分别讨论载体、资产和策略，区分记忆状态更新与管理策略演进，并从未来行为的保持、适应和迁移评价记忆作用。

**采用：**外部可寻址存储为首选；Episode、Knowledge、Skill 分别治理。内循环处理内容，外循环产出候选策略并隔离评测，记录检索/注入/使用/结果，而不以条目数量衡量成功。

**限制：**这是设计和评价框架，不是可直接部署的统一引擎。其规模分析不能当作本项目容量公式或可靠性保证；本期不做参数记忆、KV Cache 持久学习或无人监督的线上策略演化。

**限制：**生产运维不把 LLM-as-Judge 当真实成功验证，不把经验条目插入系统权限指令。多次采样/探索只在预算和隔离环境允许时评估，不为学习重复操作真实设备。
